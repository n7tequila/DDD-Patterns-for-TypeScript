## 二 · 执行流程（POST /bookings，示例工程现行代码）

1. `app/src/composition-root.ts`：`demoAuth` 解析身份头，写入 `actor`。
2. `booking/src/interfaces/http/routes.ts`：zod 解析请求体 → `toBookRoomCommand` 用领域构造函数建命令 → `BookRoom.execute`。
3. `booking/src/application/book-room.ts`：事务外经 `RoomCatalogAdapter` 查会议室（ACL 用 `roomViewV1` 解析 room-catalog 门面的返回）→ 事务内 `existsOverlapping` → `Booking.create` → `save` → `outbox.append`。
4. `booking/src/infrastructure/persistence/drizzle-unit-of-work.ts`：同步事务；作用域方法先 `assertOpen()`；乐观锁用 `RETURNING`。
5. 路由按 `kind` 映射 Result 失败、按 `code` 映射抛出的错误。

## 三 · 核心机制

- **工作单元三道防线**：端口类型 `NotPromise<T>` 拒绝 async 回调；回调只拿到绑定在事务上的作用域，拿不到 `tx`；事务结束后作用域关闭，泄漏的作用域写入时抛 `TransactionClosedError`。第三道是本批新加的运行时防线，针对 B3 实测的"句柄逃出后静默自动提交"。
- **模块工厂作为公开入口**：每个上下文的 `index.ts` 只导出 `createXxxModule(deps)`、类型与建表语句；组装入口只创建运行时适配器（数据库、时钟、ID、服务器）交给各模块，从不 import 上下文的基础设施。
- **深层 import 两层拦截**：经包名的深层 import 被 `exports` 挡住（Bun 与 tsc 报找不到模块，dependency-cruiser 的 `no-unresolvable` 报错）；经相对路径的深层 import 由 `no-deep-imports-across-packages` 拦截。

## 六 · 我替你定的 12 个决定

1. **TypeScript 固定 6.0.x**：实测 dependency-cruiser 18.7.2 不支持 TypeScript 7（报 missing-tsc-transpiler，会漏掉 TS 源码）；typescript-eslint 8.72.1 声明 `typescript <6.1.0`。放弃了"用 7"。代价：拿不到 7 的编译速度，等两个工具支持后再升。
2. **上下文的公开入口是模块工厂**：`index.ts` 导出 `createXxxModule(deps)`，不导出类。放弃了"组装入口逐个 new 各上下文的适配器"。
3. **interfaces 层可 import 领域的构造函数、值对象与错误**，用于建命令；不得 import 基础设施、仓储或调用聚合方法。工具只强制"不碰基础设施"，其余靠审查。原 SKILL.md 写的"只 import application"过严，与装配器示例矛盾，已改。
4. **工作单元加运行时防线**：事务结束后作用域关闭，泄漏使用抛 `TransactionClosedError`。代价：每个仓储方法多一次判断。
5. **RoomId、MemberId 放共享内核**，BookingId 留在 booking。
6. **乐观锁用 `RETURNING` 判断更新行数**，因为 Drizzle 的 bun-sqlite 驱动把 `run()` 的返回值标为 `void`。
7. **示例用 `CREATE TABLE IF NOT EXISTS` 建表**，由组装入口执行，不用 drizzle-kit 迁移；绑定文档里写明真实项目通常用迁移工具。
8. **演示鉴权信任请求头**，在代码注释与示例 README 中注明上线前必须替换。
9. **取消他人预订返回 Result `NotAllowed`**（应用层先调守卫），领域方法被绕过时仍抛出；管理员可取消任何预订。
10. **不发布的内部事件（`MemberCheckedIn`）不写 outbox**：装配函数返回 `undefined` 时跳过。
11. **relay 最多重试 5 次、至少投递一次、每行一个小事务**；没有实现退避等待，见第七节。
12. **测试文件不参与依赖检查**：测试可以触及本包内部，但不得引入生产代码不允许的依赖。

**第 3 问的补充实测（2026-11-03，drizzle-kit 0.31.11、Drizzle 0.45.4、Bun 1.3.12）**：

- `drizzle-kit generate` 正常生成 `drizzle/0000_init.sql` 与 `meta/_journal.json`；从源码运行 `migrate()` 建表成功。
- 编译成单文件程序后，在没有 `drizzle` 目录的位置运行，`migrate()` 报 `Can't find meta/_journal.json file`：官方迁移器运行时从磁盘读目录，单文件程序里没有。
- 改为把 journal（JSON import）与各迁移 SQL（`with { type: "text" }` import）编译进程序，用约 25 行的内嵌迁移器按 journal 顺序逐个在事务里执行并记录：编译后的程序首次运行应用 `0000_init`，再次运行不重复应用。

更正：决定 7 的理由"示例少一个工具"偏弱。drizzle-kit 可用，单文件程序的问题有已实测的解法，代价是一个内嵌迁移器和每个迁移文件一条 import。

**第 3 问的实施（2026-11-03）**：

- 两个上下文各有 `drizzle.config.ts`，`NAME=<名> bun run db:generate` 依次生成迁移并运行 `scripts/embed-migrations.ts` 生成 `src/infrastructure/migrations.generated.ts`。
- 新增 `packages/sqlite-support`（基础设施层共享包）：`migrateEmbedded(sqlite, owner, migrations)`，迁移记录按上下文区分。
- 删除 `BOOKING_DDL`、`ROOM_CATALOG_DDL`；各上下文导出 `migrateBooking` / `migrateRoomCatalog`，组装入口启动时调用。原 DDL 里的 `bookings_room_time` 索引改为在 Drizzle schema 中声明。
- ESLint 资产的 `files` 收窄到 `packages/*/src` 与 `packages/*/test`（原写法会把 `drizzle.config.ts` 交给类型感知解析而报错）。
- 验证：`bun run check` 退出码 0，测试 26 个全过（新增"迁移只应用一次且建出索引"）；编译后的程序放到没有 `drizzle/` 目录的新位置，首次启动建库、第二次启动不重复迁移，订房请求均返回 `ROOM_NOT_FOUND`；破坏验证：迁移器不记录已应用的标签时，新增测试变红。
- 文档：bindings/drizzle.md「Schema Creation」改写为「Migrations In A Single-File Binary」；typescript-ddd-layout 的公开入口改为导出迁移函数；示例 README 加 db:generate 用法。
